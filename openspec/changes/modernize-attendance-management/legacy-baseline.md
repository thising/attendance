## 读取范围与工具

[tools/inspect_legacy.py](../../../tools/inspect_legacy.py) 仅依赖 Python 标准库。运行方式：

```sh
python3 tools/inspect_legacy.py managedb.sqlite3
```

工具通过 SQLite URI `mode=ro` 打开已存在的文件，启用 `PRAGMA query_only=ON`，并以 authorizer 拒绝写 SQL、ATTACH、可写 PRAGMA 和扩展加载。整个读取在同一个只读事务快照中进行，结束时回滚并关闭连接；不会导入 Django 配置、模型或执行迁移。路径不存在时直接失败，不会创建空数据库。遇到读取错误仅输出异常类型，避免异常消息夹带数据。

输出为 JSON：表/列/索引/外键结构、Django 迁移账本、表行数、重复组数量、孤儿引用数量、跨班报告数量、日期跨度和有报告却无月汇总的分组数量。结构默认值仅报告是否存在，不输出任意 SQL 默认表达式。没有姓名、学号、班级/活动名称、密码、访问码、会话内容或逐条业务记录；重复检测只输出组数，不输出分组键。`null` 表示缺少执行该项检查所需的表或列，不能解释为 0。

不得因为编号都以 `0002` 开头，就把两条记录视作同一迁移；不得据最终表结构将缺失迁移伪造为空操作、删除账本记录、覆盖原初始迁移或直接执行 `--fake` / `--fake-initial`。缺失文件可能涉及历史模型状态或数据变换，最终 schema 无法还原这些过程。应先追溯有授权的部署代码或备份；如最终无法恢复，只能在副本上形成明确的迁移协调方案、记录无法证明的内容，再决定是否可接受。此次预检未修改迁移账本。

## 与现存 0001 + 0002 的结构比对

五张业务表的列集合与上述两份迁移累计结果一致，无缺列、无多列；已人工核对 PRAGMA 输出中的字段类型/长度、非空、主键、外键目标及相关索引：

| 表 | 已核对的结构 |
| --- | --- |
| manage_class | 5 列；整型主键及负责人外键；classname 为 varchar(30)，sharecode 为 varchar(10)，managecode 为 varchar(20)；sharecode 有唯一索引 |
| manage_student | 5 列；整型主键及班级外键；number/name 为 varchar(20)，sex 为 varchar(8) |
| manage_activity | 6 列；整型主键及班级外键；time 为 datetime，name 为 varchar(30)，activity_type/status 为 varchar(20) |
| manage_report | 6 列；整型主键、活动和学生外键；status/level/discipline 均为 varchar(20) |
| manage_summarycount | 13 列；整型主键、学生外键、year/month 及九类整型计数 |

上述列均声明非空；业务外键有普通索引。原迁移的 ORM 级 `CASCADE` 不等于 SQLite DDL 的 `ON DELETE CASCADE`，现场外键元数据的删除动作是 `NO ACTION`，不应因此误判迁移失配。数据库中尚无学生、报告和月汇总的复合业务唯一约束；本次样本恰无重复，不代表可以跳过增量约束迁移前的检查。

工具的 `legacy_column_compatibility` **只自动比较列名集合**；完整 schema 元数据另行输出。上述人工核对仅支持已列结构属性相符，不证明缺失迁移没有其他作用，也不证明 Django 模型状态完全相同。例如原 `0001` 的活动类型 choices 没有“违纪”，而旧模型有该选项；Python 字段默认值、choices、数据迁移和实际历史执行顺序都不能仅由 SQLite 列结构证明。恢复迁移基线后仍需在隔离环境完成模型状态差异检查和空库建立。

## 升级与回滚检查建议

1. **在副本演练前固定证据。** 从得到授权的数据库制作一致性备份；存在 WAL 时使用 SQLite 在线备份接口或停写后一致复制，不能只复制主文件而丢失未合并的 WAL。记录来源、代码/依赖版本、备份校验信息及恢复步骤，限制备份访问范围。此工具只读检查，不负责制作或替代备份。
2. **先协调迁移基线。** 恢复现存原始迁移进入版本控制，追溯缺失 `0037`；在独立环境检查迁移图、实际 schema 和账本，分别验证空库安装与旧库副本升级。新字段/约束使用增量迁移；升级前预检再次运行，发现重复或跨班数据时形成差异清单，不自动合并或删除。
3. **保留历史依据再比较新算法。** 本次发现的业务记录都落在 2023 年秋季，但旧表没有独立的学期名单、权重版本和最终归档成绩。不能用现有 660 人名单证明当期全部成员，也不能用两个月的汇总行数量代替完整学期计分月份。按已批准提案，入账立即生效、自然月补基础分、春季 2–7 月/秋季 9–1 月、已结束学期只读；副本上分别保留旧报表结果和新算法候选结果，列出差异及无法还原的历史信息。历史成绩差异未经另行审核不得静默覆盖。
4. **副本升级验收。** 对比班级、学生、活动、报告等原始实体及关联数量，验证原始记录守恒、全部报告关联范围、新增唯一约束、月份/日期保留、密码散列转换及会话失效策略；以合成数据验证历史写入拒绝和规则/名单冻结。密码迁移等变化只在副本先做，日志和验收产物不含明文凭据。
5. **先证明能恢复。** 在独立目标恢复升级前备份，运行本工具比较原基线的 schema、账本、计数和日期跨度，再用原代码与原依赖做启动和抽样验收。正式回滚必须恢复经过验证的代码、环境、数据库组合，不能让旧代码直接连接新 schema。正式部署应有停写窗口及失败回退条件；获得部署授权后才执行服务/真实库变更。

## 工具实际验证

使用 `/private/tmp` 下临时合成 SQLite 文件验证，测试完成后删除临时目录，未写入真实数据库：

- 合成库放入姓名、学号、活动名、明文密码、访问码和会话的独立标记，JSON 输出不含任何标记；非法日期原值也未输出。
- 5 类重复组各构造 1 组，跨班报告构造 2 条，有报告但缺月汇总构造 1 组；聚合结果均符合预期。
- INSERT、UPDATE、DELETE、DROP TABLE、ATTACH、关闭 query_only、VACUUM INTO 共 7 类语句被拒绝。
- 仅在合成连接中移除 authorizer 并关闭 query_only 后，UPDATE 仍被 URI `mode=ro` 拒绝，确认并非只依赖附加保护。
- 合成数据库检查前后 SHA-256 相同；包含 `#`、`?` 的文件名正确解析；不存在路径不创建文件，空库输出缺失项而非崩溃。

本节证明只读预检工具的保护和合成统计行为，不代表应用迁移、线上验证或历史成绩审核已完成。
